# CLAUDE.md

Context for Claude Code sessions on this repo. Read the README for setup
steps; this file covers how the project is built and worked on.

## What this is

A personal reminder app, built as a learning project. The owner is learning
web development end to end, so **explanation matters as much as working code**.

Two standing preferences:

- **Keep replies short.** Long, dense answers are unhelpful here. A few
  sentences, then stop. Offer detail rather than front-loading it.
- **Optimise for readability over cleverness.** The code is meant to be read
  and understood, not admired.

## Stack

Plain HTML, CSS and JavaScript. No framework, no build step, no `npm install`.
The only dependency is the Supabase JS client, loaded from a CDN in
`index.html`.

- `index.html` — auth screen and the logged-in app
- `style.css` — all styling; colours are custom properties on `:root`
- `app.js` — Supabase client, auth, CRUD, list and calendar rendering
- `schema.sql` — table plus Row Level Security policies
- `README.md` — setup and deployment

Hosted on GitHub Pages from `main`. Data and auth are Supabase.

Don't introduce a framework, a bundler or a package manager without asking.
The absence of a build step is deliberate — the owner can open `index.html`
and see the whole thing.

## Workflow

The owner has given standing permission to **merge to `main` directly** —
work on a branch, merge when it works, no pull request. PRs only for
something large they'd want to read first.

```sh
git checkout -B <branch> origin/main
# ... work, verify ...
git checkout main && git merge --no-ff <branch> && git push origin main
```

`main` is what GitHub Pages serves, so a bad merge breaks the live site.
Verify before merging.

The branch name `claude/web-app-end-to-end-bl0krj` is auto-generated by
Claude Code on the web, not a convention worth preserving.

## Testing

There is no test suite. Changes are verified by driving the real app in
Chromium via Playwright, with the Supabase CDN script stubbed out by a fake
client, so no network or live database is needed:

```js
await page.route('**/@supabase/supabase-js@2', route => route.fulfill({
  contentType: 'application/javascript',
  body: '/* window.supabase = { createClient() { ... } } */',
}));
```

Scripts live in the scratchpad, not the repo. This has caught real bugs
(a success message being cleared immediately, a mobile CSS rule overriding
the top bar), so it's worth doing rather than eyeballing the diff.

Worth checking on any UI change: both colour schemes, and no horizontal
overflow at 375px.

**This sandbox cannot reach `supabase.co` or `github.io`** — the network
policy returns 403 at the proxy. So the live site and the real backend can
only be tested by the owner. Say so rather than claiming something is
verified when it isn't.

## Key decisions

**Queries don't filter by user, on purpose.** `loadReminders()` is a bare
`select("*")`. The RLS policies in `schema.sql` make Postgres scope every
query to `auth.uid()`, taken from the signed login token. Enforcing it in the
database means it also holds against hand-crafted requests. Don't "fix" this
by adding a `.eq("user_id", ...)` filter.

**The publishable key is committed deliberately.** It's designed to be served
to browsers; it identifies the project rather than authenticating anyone. The
**secret** key (formerly `service_role`) bypasses RLS and must never appear in
this repo.

**Any new table needs RLS enabled.** The project has automatic RLS switched
on, so new tables start locked down, but say so explicitly in the SQL too.

**The app can't tell whether an email is already registered.** Supabase won't
answer that from the browser, so nobody can probe for registered users. Hence
the login/signup mode toggle rather than detecting it.

## Supabase configuration

Things that bit us, so they're worth knowing:

- **Site URL** must be `https://fjbenson.github.io/reminders/`, path included.
  It defaults to `localhost:3000`, and the value is **baked into each email at
  send time** — changing it never repairs emails already sent, so any fix
  needs a fresh email to test.
- **Email confirmation is currently off**, so signup logs the user straight in.
- The **built-in SMTP is rate-limited** to a couple of messages an hour. Real
  volume needs custom SMTP (Resend, SendGrid, Postmark).
- Auth is on by default. `auth.users` and `auth.uid()` exist without setup.

Schema and settings changes are dashboard work the owner does by hand.
Give them the SQL or the exact click path; don't claim to have applied it.
